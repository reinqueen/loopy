# Milestone Planning and Conditional Guides

Use this internal reference when the single Loopy skill recognizes “plan this Milestone,” “pick up this Planned Milestone,” or “continue planning.” Never expose this route as a separate skill or command.

Start only from explicitly named committed Definitions. Load synchronized lifecycle state and summarize the outcome, authoritative Definition revision, dependencies, participants, blockers, known work location, and one next action. Beginning planning makes the Milestone Active; Plan readiness remains distinct from implementation authority.

Inherit confirmed meaning and authorized evidence. Use the shared Socratic move-selection loop for delivery approach, outcome-first work units, implementation choices, typed dependencies, safe parallel boundaries, checks and evidence intent, risks, workspace disposition, and release impact. Any Human may contribute; ask what the participants know or intend before recommending. When finalizing a consequential planning choice, confirm the affected responsibility. Route a material change to committed Product meaning or priority through Change Management.

Record a proposed Build/evaluation budget in the Plan. Recommend focused independent checkpoints only for justified risk or integration boundaries, never mechanically per Work Unit; zero focused checkpoints is valid. Always record exactly one required final integrated independent evaluation boundary last. For each boundary record readable scope/trigger, applicable Work Units, risk basis, required status, and a nonnegative correction-cycle limit—the maximum corrected new candidates allowed after an initial failure, each requiring reevaluation. Plan readiness requires this formal boundary, but review remains routine and grants no Build authority.

Share a question across Plans only when the answer applies identically. Split immediately on different approach, dependency, risk, workspace, or evidence needs. One blocked Plan does not block an independent Plan.

Keep one-time decisions in `Plan.md`. Trigger `Architecture.md`, `Demo-Strategy.md`, or `Release-Strategy.md` only for reusable durable guidance. Missing guide input blocks readiness only when implementation cannot safely begin without it; otherwise record a just-in-time trigger. A new or materially revised guide requires its responsible perspective's same-revision confirmation. The last substantive answer may confirm it; do not add Plan approval or generic reapproval.

Persist meaningful canonical updates without repeatedly presenting drafts. Publish current synchronized views at explicit request, useful pause/block, review readiness, status, and ready-for-implementation. Stop before implementation. Do not create a worktree, change product files, run Proof, perform a Demo, or create Release artifacts.

Delivery-safety summaries are Engine-rendered views of typed relationships, never separate freehand state. Required-before work appears as a numbered, tree-like adjacency flow; only explicit safe claims appear under **Can happen in parallel**; blocked claims appear under **Needs coordination**. Helpful or merely independent relationships stay in the detailed sections and never become safety claims.

Before any Planning move or publication, compare the captured Product, Engineering, Roadmap, and Definition-state revisions with canonical state. If any changed, report the exact old and current anchors and stop without writing. Inspect authorized evidence and use the shared move-selection loop to determine whether the Plan remains coherent. Only then submit explicit semantic revalidation against those exact current anchors; never silently refresh them. Revalidation preserves history, clears prior Plan review readiness, and leaves unresolved Plan blockers intact.
