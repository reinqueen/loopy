# Milestone Planning Engine input

This is internal Host-AI guidance. Keep Plan identities, JSON, hashes, and commands out of the Human experience.

- `planning-init` takes a JSON array of distinct explicitly named committed Definition identities. It creates independent Plan state and no implementation workspace.
- `planning-apply` takes one closed update with `planId`, actor name/responsibility, and changed content, Host coherence, participants, workspace disposition, guide triggers, or guide drafts. Work-unit keys are internal. Required-before relationships must be acyclic; helpful and independent relationships do not impose order. `content.evaluationBoundaries` may contain zero or more `focused-independent` checkpoints followed by exactly one required `final-integrated-independent` boundary for a ready Plan. Each record contains `checkpoint`, distinct known `workUnits`, `trigger`, `reason`, nonnegative integer `correctionCycleLimit`, and boolean `required`. The Engine orders focused boundaries by applicable Work Unit order and the final boundary last.
- `planning-review` names Plans and optional guide kinds. It records non-approval Plan review only when formal coverage and Host coherence are present; guides become ready for their responsible perspective's confirmation.
- `planning-confirm-guides` confirms distinct ready reusable guides at their current revisions. It never approves a Plan or authorizes a later stage.
- Every Planning operation first checks the captured Product, Engineering, Roadmap, and Definition-state revisions. A mismatch rejects without mutation. `planning-revalidate` takes the exact current `reviewedAnchors`, actor name/responsibility, and a substantive Host semantic-review `basis`; it updates anchors only through that explicit action, appends Plan history, and clears prior Plan review readiness.
- `planning-interrupt`, `planning-resume`, `planning-render`, `planning-stale`, and `planning-status` preserve the shared canonical-state/public-view boundary. Resume requires explicit stale-view repair first.

The Host AI owns semantic coherence, meaningful work-unit boundaries, parallel safety, evaluation risk/budget recommendations, foundation revalidation, and whether a guide is truly needed. The Engine validates declared formal state only, including the mandatory final evaluation boundary, nonnegative correction-cycle limits, known Work Unit references, stable order, and rejection of a `safe` parallel claim when any claimed pair is connected in either direction by a direct or transitive `required-before` path. A separate-workspace disposition is a recommendation/record, not permission to create a Git worktree. Ready-for-implementation is routing, not implementation or evaluation activation authority.
