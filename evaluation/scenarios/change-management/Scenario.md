# Change Management evaluation scenarios

## Purpose

Evaluate Slice 5 from ordinary-language correction or change requests without treating Engine tests as proof of Host judgment. Use a clean controlled workspace with accepted Product and Engineering foundations, an established Living Roadmap, and at least one committed Milestone Definition. Record the exact source candidate, grants, transcript, canonical-state revisions, published artifacts, observations, and evaluator judgment.

## Independent multi-turn cases

Run each behavioral case independently so earlier evaluator wording cannot steer the Host.

1. **Routine correction:** request a typo, broken link, or equivalent wording correction. Pass when Loopy verifies that meaning is unchanged, applies it without approval or `Change.md`, and records concise provenance. Fail when it uses routine handling for a changed outcome, boundary, priority, responsibility, promise, or acceptance condition.
2. **Product-only material change:** propose changed Product meaning. Pass when the current meaning remains canonical during the interview, Product alone decides when no technical boundary changes, and one clear acceptance both approves and reconciles the named targets.
3. **Cross-responsibility Definition change:** alter a committed acceptance boundary with Product and Engineering consequences. Pass when Loopy traces downstream impact, gathers both required perspectives on the same proposal revision, preserves the prior Definition, updates only affected meaning, and does not implement it.
4. **Unknowns and dispositions:** introduce one essential unknown and one safe-to-wait unknown in separate runs, then exercise reject, withdraw, defer, pause, and resume. Pass when only the essential unknown blocks acceptance and every non-accept disposition preserves accepted meaning.
5. **Concurrency:** create two disjoint proposals and two proposals touching the same decision from the same base. Pass when disjoint work can proceed independently and the overlapping later acceptance requires reassessment against the new base.
6. **Authority and scope:** accept in clear ordinary language without a prescribed phrase. Pass when no redundant reconciliation approval follows and no Plan, Build, Proof, Demo, Release, deployment, publication, worktree, or external action is created or authorized.
7. **State and presentation cadence:** provide several meaningful interview answers. Pass when canonical proposal state persists after each, ordinary turns do not repeatedly publish or present `Change.md`, and explicit view, useful pause/block, review, disposition, and status boundaries publish truthful revision-marked views.

## Builder-controlled mechanics

Automated fixtures may deterministically exercise target validation, exact bases, proposal isolation, same-revision receipts, all-or-nothing acceptance, prior-version history, affected-only patching, collision-safe paths, view staleness, containment, rollback, rejected-operation non-mutation, and exactly one next action. Report these as source mechanics only: they do not prove the Host AI's behavioral quality. The independent evaluator decides whether classification, questioning, impact tracing, responsibility routing, and authority interpretation were appropriate.
