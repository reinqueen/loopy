# Golden Committed Definition to Milestone Plan

## Purpose

Carry the existing golden Product, Engineering, Roadmap, and committed Definition state into a bounded Milestone Plan. This is a controlled builder scenario for deterministic behavior, not independent proof of planning judgment.

## Path and expected observations

1. In a fresh disposable workspace, explicitly name one committed Definition and enter Planning in ordinary language.
2. Carry required-before, helpful/non-blocking, and independent/potentially-parallel Roadmap relationships through Definition inheritance. Verify the Milestone becomes Active in the synchronized Roadmap and receives one readable `Plan.md` beside its authoritative `Definition.md`.
3. Preserve the committed outcome and acceptance boundary. Add outcome-first work units, completion observations, checks, typed dependencies, participants, workspace intent, risks, and one project next action. Record zero or more risk-justified focused independent evaluation checkpoints and exactly one required final integrated independent boundary; include nonnegative correction-cycle limits and keep the final boundary last.
4. Record unrelated or helpful work without inventing required order. Reject a required-before cycle with no state, history, or view mutation.
5. Reject every safe-parallel claim whose units have a direct or transitive required-before path in either direction. Advance each foundation revision through controlled lifecycle operations; verify every Planning operation rejects without mutation until an explicit exact-anchor Host revalidation records history and clears prior review readiness.
6. Keep an ordinary incomplete interview update in canonical state without republishing the Plan. Publish on review, useful pause/block, explicit render/status, or readiness.
7. Review a coherent Plan without approval and verify `ready-for-implementation` grants no implementation or tool authority.
8. Verify no worktree, Build, Proof, Demo, Release, publication, deployment, or target-product change is created.

## Human-readable output assertion

`Plan.md` includes one portable fenced **Delivery safety** summary only when canonical safety relationships apply. Exercise a linear chain, a branch, a convergence, multiple roots, and a disconnected required chain; each direct edge appears beneath its numbered source in stable Work Unit order. Only an explicit safe claim appears under **Can happen in parallel**. A blocked claim appears under **Needs coordination** with its reason. Helpful and merely independent dependencies remain in the detailed sections and do not appear in the quick summary. With none of these relationships, the summary is absent.

`Roadmap.md` shows required order and canonical independent relationships as **Potentially parallel**, never as implementation-safe. Helpful relationships remain detailed. Unresolved or contradictory relationship meaning appears under **Needs coordination**. Normal Roadmap-to-Definition inheritance produces no duplicate, stale repair regenerates the same summary, and all Planning publication paths preserve it alongside exactly one project next action.

`Plan.md` also includes one readable **Build and evaluation boundaries** table. A low-risk Plan may omit focused checkpoints but cannot become ready without exactly one required final integrated independent boundary. The table follows Work Unit order with final integrated evaluation last and defines a correction-cycle limit as corrected new candidates allowed after the initial failed evaluation; zero is valid.

## Pass boundary

The deterministic path passes when state, history, routing, and synchronized views satisfy these observations. Host semantic quality requires the separate independent conversation scenario.
