# Milestone Planning Interview Quality

## Protocol

Run each case as a fresh, unsteered multi-turn conversation against the exact candidate. Preserve the candidate commit, workspace and authorized-context grants, transcript, generated artifacts, observations, and evaluator judgment. Do not provide the expected questions to the Host. Structural tests cannot establish these behaviors.

## Cases

1. **Inherited meaning:** Start from a committed Definition with useful Product and Engineering evidence. Loopy should summarize and reuse it, inspect authorized facts, and ask only unresolved planning decisions.
2. **Outcome-first decomposition:** Use a Milestone spanning several components. Work units should express coherent outcome contributions rather than one unit per component, file, or participant.
3. **Dependency and parallel safety:** Include independent work plus a shared interface or schema risk. Loopy should distinguish required-before, helpful, and potentially parallel relationships, and should not call work safely parallel until the shared conflict is resolved.
4. **Responsibility boundary:** Let planning reveal a possible Product consequence. Loopy should ask Product only about the affected meaning or route a material change through Change Management, while retaining Engineering ownership of delivery choices.
5. **Conditional guides:** Include one reusable specialist decision that blocks safe implementation and one useful only later. Loopy should obtain current responsible confirmation for the first and route the second just in time without turning Planning into a setup gate.
6. **Low fatigue and stopping:** The Host should use the shared after-response move-selection loop, avoid Plan approval, accept a final substantive specialist response as guide confirmation when clear, and stop before implementation once current-stage coverage is sufficient.
7. **Independent Milestones:** Plan two named Milestones with divergent risks. Shared questions should split when meaning diverges, and one blocked Plan should not prevent the other from becoming ready.

## Evaluation boundary

A pass requires grounded recommendations, calm prerequisite-aware questioning, truthful artifacts, and a clear stop before implementation. Builder-authored fixtures or unit tests are not substitutes for this independent evaluation.
